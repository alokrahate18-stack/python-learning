# Day 1
## Topic: Python Basics, Syntax, `print()` and Comments
## Theory
### 1. What is Python?
Python is a high-level, interpreted, general-purpose programming language.
It is designed to make code readable and easy to write. Python is dynamically typed, meaning you do not have to explicitly declare the type of a variable before using it.
```
age = 20
name = "Alok"
```
In the example above, Python automatically understands that:
- `age` refers to an integer
- `name` refers to a string
***
### 2. Python program execution
Python source code is usually written in a file ending with `.py`.
```text
Python Code
    ↓
Python Interpreter
    ↓
Execution
    ↓
Output
```
Python is commonly called an interpreted language because the Python interpreter runs the program. In practice, Python may also compile source code into bytecode internally, but you normally run Python files directly without manually compiling them first.
***
Day 1: Variables, Values, and Assignment
Today’s goal is to understand how Python stores and uses information. We will not study tuples, lists, sets, or dictionaries yet.

1. What Is a Value?
A value is a piece of data used by a program.

Examples:

python
25
3.14
"Python"
True
None
These values have different types:

python
print(type(25))       # <class 'int'>
print(type(3.14))     # <class 'float'>
print(type("Python")) # <class 'str'>
print(type(True))     # <class 'bool'>
print(type(None))     # <class 'NoneType'>
Python’s main basic data types are:

Type	Meaning	Example
int	Whole number	25
float	Decimal number	3.14
str	Text	"Python"
bool	Truth value	True or False
NoneType	No value	None
2. What Is a Variable?
A variable is a name that refers to a value.

python
age = 20
Here:

age is the variable name.

20 is the value.

= is the assignment operator.

You can use the variable later:

python
age = 20

print(age)
print(age + 1)
Output:

text
20
21
The statement age = 20 does not mean “age is permanently equal to 20.” It means Python should associate the name age with the value 20.

3. Assignment
Assignment stores or reassigns a value.

python
age = 20
print(age)

age = 21
print(age)
Output:

text
20
21
The second assignment changes what age refers to.

You can also assign different types at different times:

python
value = 10
print(value, type(value))

value = "ten"
print(value, type(value))
Python allows this because it is dynamically typed. The variable name does not have a permanently fixed type.

4. Variable Names
A variable name may contain:

Letters: a to z, A to Z

Digits: 0 to 9

Underscores: _

However:

A name cannot begin with a digit.

A name cannot contain spaces.

A name cannot be a Python keyword.

Names are case-sensitive.

Valid names:

python
student_name = "Vishal"
age2 = 20
_marks = 85
total_marks = 450
Invalid names:

python
# 2age = 20          # Cannot begin with a digit
# student name = ""  # Spaces are not allowed
# class = "Python"   # "class" is a keyword
5. Case Sensitivity
Python treats uppercase and lowercase names as different:

python
age = 20
Age = 30
AGE = 40

print(age)
print(Age)
print(AGE)
These are three different variables.

Use consistent lowercase snake_case names:

python
student_name = "Vishal"
total_marks = 450
passing_percentage = 40
Avoid unclear names:

python
x = "Vishal"
a = 450
b = 40
Short names are acceptable for temporary values or loop counters, but descriptive names are better for most programs.

6. Do Not Shadow Built-ins
Python already provides built-in functions and types. Do not use their names for your variables.

Avoid:

python
list = "students"
str = "text"
type = "number"
id = 101
For example:

python
list = [1, 2, 3]
print(list("abc"))
This causes an error because list no longer refers to Python’s built-in list() function.

Use names such as:

python
student_names = ["Vishal", "Rohit", "Ajay"]
text_value = "abc"
number_type = "integer"
student_id = 101
We will study lists later, but this naming rule is important now.

7. Multiple Assignment
Python allows multiple variables to be assigned in one statement:

python
name, age, city = "Vishal", 20, "Nagpur"

print(name)
print(age)
print(city)
Each variable receives the corresponding value.

This is also valid:

python
first_name = last_name = "Vishal"

print(first_name)
print(last_name)
Both variables refer to the same string value. For immutable basic values such as strings and integers, this is normally straightforward.

8. Assignment Is Not Comparison
The single equal sign assigns a value:

python
age = 20
The double equal sign compares values:

python
print(age == 20)  # True
print(age == 25)  # False
Do not confuse them:

Operator	Purpose
=	Assignment
==	Equality comparison
We will study comparisons in detail later.

9. Inspecting Values
Use print() to display values:

python
student_name = "Vishal"
age = 20

print(student_name)
print(age)
Use type() to inspect the data type:

python
student_name = "Vishal"
age = 20

print(type(student_name))
print(type(age))
You can print multiple values:

python
student_name = "Vishal"
age = 20
city = "Nagpur"

print(student_name, age, city)
10. Comments
Comments are ignored by Python and are used to explain code.

python
# This stores the student's age.
age = 20
A comment begins with #.

Use comments to explain:

Why something is done.

A non-obvious decision.

Avoid writing comments that merely repeat the code:

python

age = 20
A better comment would explain context:

python
# The minimum age for this application is 18.
age = 20

Day 3 (Full): Operators
Theory

1. Arithmetic operators, every one, with the edge cases

python
7 + 3      # 10
7 - 3      # 4
7 * 3      # 21
7 / 3      # 2.333... — TRUE division, ALWAYS returns a float, even 10/2 = 5.0, not 5
7 // 3     # 2 — FLOOR division, rounds toward NEGATIVE infinity
7 % 3      # 1 — remainder
7 ** 3     # 343 — exponent; also works with fractions: 9 ** 0.5 = 3.0 (square root)

2. Floor division with negatives — the real trap, worth memorizing precisely

python
7 // 2      # 3
-7 // 2      # -4, NOT -3! Floors toward negative infinity, not toward zero
7 // -2       # -4
-7 // -2        # 3

This matters because many people assume // just “chops off the decimal” like int() does — it doesn’t. int(-7/2) gives -3 (truncates toward zero); -7 // 2 gives -4 (floors toward negative infinity). They genuinely differ on negative numbers.

3. Modulo with negatives — follows the same floor logic

python
7 % 3        # 1
-7 % 3         # 2, not -1! Python's % always returns a result with the SAME SIGN as the divisor
7 % -3           # -2

Rule: the sign of the result always matches the sign of the right-hand operand.

4. Comparison operators — all six, always return bool

python
== != > < >= <=

Comparing different types that can’t sensibly compare (5 < "5") raises TypeError in modern Python — unlike ==, which just quietly returns False instead of erroring.

5. Logical operators — full behavior, not just True/False

python
True and False    # False
True or False       # True
not True               # False

The crucial detail: and/or don’t just return True/False — they return one of the actual operand values:

python
0 or "default"          # "default" — first operand is falsy, returns the SECOND
5 or "default"            # 5 — first operand is truthy, returns it immediately, never looks at second
"" and "backup"             # "" — first operand is falsy, returns it immediately
"x" and "backup"               # "backup" — first is truthy, so returns the SECOND

Mental rule: or returns the first truthy value (or the last value if none are truthy). and returns the first falsy value (or the last value if none are falsy).

6. Short-circuit evaluation — the mechanism, and why it’s used deliberately

python
False and expensive_function()    # expensive_function() is NEVER called — result is already known
True or expensive_function()        # expensive_function() is NEVER called either

user = None
if user is not None and user.is_active:   # safe — user.is_active only checked if user isn't None
    print("active")

This isn’t just an optimization — it’s a real safety pattern you’ll use constantly, especially once exceptions and object attributes are in regular use.

7. Bitwise operators — genuinely different from logical ones, full table

python
5 & 3      # 1  — AND, bit by bit:   0101 & 0011 = 0001
5 | 3      # 7  — OR, bit by bit:    0101 | 0011 = 0111
5 ^ 3      # 6  — XOR (exactly one bit differs): 0101 ^ 0011 = 0110
~5         # -6 — NOT, flips all bits (uses two's complement, so ~n = -n-1)
5 << 1     # 10 — shift bits left (same as multiplying by 2)
5 >> 1     # 2  — shift bits right (same as floor-dividing by 2)

These operate on the binary representation of integers — completely unrelated to logical truth/falsehood, despite &/| visually resembling and/or. This is the exact, formalized version of your 013_challenge_05 bug: age >= 18 & has_id doesn’t do what it looks like it does, because & binds tighter than >= and operates bit-by-bit on the underlying integers, not logically.

8. Assignment operators — the full set, all shorthand for “do the op, then reassign”

python
x += 1      # x = x + 1
x -= 1       # x = x - 1
x *= 2        # x = x * 2
x /= 2         # x = x / 2
x //= 2          # x = x // 2
x %= 2             # x = x % 2
x **= 2              # x = x ** 2
x &= y                 # x = x & y   (bitwise)
x |= y                   # x = x | y
x ^= y                     # x = x ^ y

For mutable objects, some of these behave subtly differently from the “full” form — list += [1,2] modifies the list in place (like .extend()), while list = list + [1,2] creates a new list. Usually invisible, but matters if another variable also references that same list.

9. Identity (is) vs equality (==) — the full distinction

python
a = [1, 2, 3]
b = [1, 2, 3]
a == b          # True — same VALUES
a is b            # False — different OBJECTS in memory, even though values match

c = a
a is c              # True — c and a point to the SAME object

The integer/string caching trap, worth knowing precisely: Python caches small integers (-5 to 256) and some short strings for efficiency, so a is b can accidentally return True for separately-created small values even without c = a:

python
x = 200
y = 200
x is y          # True — both happen to be the same cached object (implementation detail, don't rely on this)

x = 300
y = 300
x is y            # often False — outside the cached range, separate objects — but NOT guaranteed by the language

Rule to actually live by: never use is/is not for value comparison. Only use it for is None / is not None — that’s the one case where is is the universally correct, idiomatic tool, because None is a true singleton (only one None object ever exists).

10. Membership operators — in / not in, across every container type

python
"a" in "cat"             # True — substring/character check in a string
3 in [1, 2, 3]               # True — list membership
3 in (1, 2, 3)                  # True — tuple membership
"key" in {"key": 1}                # True — dict membership checks KEYS only, not values
3 in {1, 2, 3}                       # True — set membership (and this one is genuinely fast, unlike list)

11. Operator precedence — the full practical ordering, highest to lowest

()                          parentheses — always evaluated first, use freely to remove ambiguity
**                           exponent (right-to-left: 2**3**2 = 2**(3**2) = 512, not (2**3)**2)
+x  -x  ~x                     unary plus/minus/bitwise-not
*  /  //  %                      multiplication tier
+  -                               addition tier
<<  >>                                bit shifts
&                                        bitwise AND
^                                          bitwise XOR
|                                           bitwise OR
==  !=  >  <  >=  <=  is  in                comparisons (all same tier, evaluated left to right)
not                                             logical NOT
and                                                logical AND
or                                                    logical OR

Practical takeaway: ** is evaluated right-to-left (unusual — everything else is left-to-right), and not binds tighter than and/or but looser than comparisons — meaning not a == b means not (a == b), not (not a) == b. When any of this feels uncertain in real code, parentheses cost nothing and remove all doubt — professional code uses them liberally for exactly this reason, not because the writer forgot precedence rules.

12. Chained comparisons, formally, as an operator-level detail. a < b < c is not evaluated as (a < b) < c — Python evaluates it as (a < b) and (b < c), short-circuiting if the first part is False:

python
1 < 2 < 3        # True — genuinely checks both relationships
1 < 2 > 0           # True — equivalent to (1<2) and (2>0)

13. Common operator bugs, as a checklist — several already personally encountered:

&/| used where and/or was meant (013_challenge_05) — different operators entirely, not a typo-level difference.
Assuming // truncates toward zero on negatives, when it actually floors toward negative infinity.
Using is/is not for value comparison instead of ==/!= — works by coincidence sometimes, breaks unpredictably.
Forgetting and/or return actual values, not strictly True/False — surprising when the result gets stored and used downstream.
Missing parentheses changing meaning silently, especially with mixed bitwise and comparison operators — age >= 18 & has_id being the canonical example.

Day 7 (Full): Pattern Matching (match/case)
Theory

1. What match/case actually is. Introduced in Python 3.10, it’s structural pattern matching — not just a prettier if/elif/else. It doesn’t only compare values; it can look inside a value’s shape (a list’s length, a dict’s keys, an object’s attributes) and bind pieces of it to variables, all in the same step. Python checks cases top to bottom and stops at the first match — order is always significant.

2. Basic syntax and literal patterns — matching exact values:

python
match status_code:
    case 200:
        print("OK")
    case 404:
        print("Not Found")
    case 500:
        print("Server Error")
    case _:
        print("Unknown")

_ is the wildcard — “anything else.” Always goes last; Python won’t warn you if it’s not last, but anything after it becomes unreachable dead code.

3. OR patterns — multiple literals, one case, using |

python
match command:
    case "quit" | "exit" | "q":
        print("Goodbye")
    case "help" | "h" | "?":
        print("Showing help")

4. Capture patterns — binding a variable to whatever’s there

python
match point:
    case (0, 0):
        print("Origin")
    case (0, y):           # y captures whatever the second value is
        print(f"On Y-axis at {y}")
    case (x, 0):
        print(f"On X-axis at {x}")
    case (x, y):             # catches any other pair, binding both
        print(f"Somewhere at ({x}, {y})")

Order matters here specifically because of specificity — (0, 0) must come before (0, y), or the more general pattern would capture the origin case too (since y would just bind to 0). This is the exact ordering principle you already discovered yourself.

5. Sequence patterns — matching the shape of lists/tuples

python
match data:
    case []:
        print("Empty")
    case [x]:
        print(f"One item: {x}")
    case [x, y]:
        print(f"Exactly two: {x}, {y}")
    case [first, *rest]:
        print(f"First: {first}, rest: {rest}")    # *rest collects remaining items into a LIST
    case [*_]:
        print("Any length (fallback)")

*rest is just a variable name — could be *remaining, *others, anything. [first, *rest] requires at least one item; it won’t match []. case [*rest] alone matches a list of any length, including empty, binding the whole thing to rest.

A sequence pattern also matches tuples — match point: case (x, y): works the same as list patterns, since both lists and tuples count as “sequences” here. Strings are deliberately excluded from this, even though they’re iterable — case [a, b]: won’t match the string "ab" by accident.

6. Mapping patterns — matching dict shape, now that you know dicts

python
match person:
    case {"name": name, "age": age}:
        print(f"{name}, {age}")
    case {"name": name}:                 # matches even if OTHER keys also exist
        print(f"Just a name: {name}")
    case {}:
        print("Empty or no name/age keys")

Crucial difference from sequence patterns: a mapping pattern doesn’t require an exact match of keys — {"name": name} matches {"name": "Asha", "age": 20, "city": "Delhi"} just fine, binding only name. If you need to capture the rest of the dict too, use **rest:

python
case {"name": name, **rest}:
    print(name, rest)   # rest = every OTHER key-value pair

7. Guard clauses — adding an if condition to a pattern. You used this extensively in your inventory shell. The pattern must match and the guard must be True for that case to fire:

python
match parts:
    case ["add", qty, *rest] if rest and qty.isdigit():
        add_item(qty, rest)
    case ["add", *_]:
        print("Usage: add <qty> <name...>")

If the pattern matches but the guard fails, Python moves on to the next case — it doesn’t stop and fail outright. This is why you need a fallback case ["add", *_]: right after — to catch malformed add commands that matched the shape but failed the guard.

8. Class patterns — matching an object’s type and attributes (fuller sense now that OOP is close):

python
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

match shape:
    case Point(x=0, y=0):
        print("Origin point")
    case Point(x=0, y=y):
        print(f"On Y-axis at {y}")
    case Point():                  # matches ANY Point instance, regardless of x/y
        print("Some other point")
    case _:
        print("Not a point at all")

This checks isinstance(shape, Point) and destructures its attributes, in one step — something if/elif can’t do nearly as cleanly.

9. Positional class patterns, using __match_args__ (an OOP detail, previewed here):

python
class Point:
    __match_args__ = ("x", "y")      # defines positional matching order
    def __init__(self, x, y):
        self.x = x
        self.y = y

match shape:
    case Point(0, 0):           # positional, works because of __match_args__
        print("Origin")

10. Nested patterns — patterns inside patterns, for genuinely nested data:

python
match command:
    case {"action": "move", "to": (x, y)}:
        print(f"Moving to {x}, {y}")
    case {"action": "add", "item": [name, qty]}:
        print(f"Adding {qty} {name}")

11. Binding the whole match with as

python
match point:
    case (0, 0) as origin:
        print(f"Matched: {origin}")   # origin = (0, 0), the whole tuple

Useful when you need both the destructured pieces and the original whole value.

12. Literal patterns must be truly literal — a sneaky trap. You can’t use a plain variable name as a pattern to mean “match this value” — a bare name in a pattern is always treated as a capture, never a comparison:

python
expected = 5

match n:
    case expected:         # WRONG — this ALWAYS matches, binding n's value to "expected"!
        print("matched")

To compare against an existing variable’s value, use a dotted name (attribute access), which Python does treat as a value to compare, not a capture:

python
class Config:
    expected = 5

match n:
    case Config.expected:     # correct — compares against the VALUE 5
        print("matched")

This is one of the most common beginner mistakes with match/case — it’s worth remembering deliberately.

13. When to use match/case vs if/elif. match shines when you’re branching on the shape or structure of data (parsed commands, nested dicts/lists, multiple related fields at once) — exactly your inventory shell’s use case. For simple linear value comparisons, if/elif is often just as clear and more familiar to read. Neither replaces the other; they’re complementary tools.

14. Performance note. match/case isn’t meaningfully faster or slower than an equivalent if/elif chain for simple cases — its value is readability and safety for structural checks, not speed.

That’s pattern matching at full depth — the class-pattern section (points 8-9) will connect directly once we’re deeper into OOP, since __match_args__ is itself a class feature.

range(5)             # 0,1,2,3,4 — stop is exclusive
range(2, 5)            # 2,3,4
range(0, 10, 2)          # 0,2,4,6,8 — step
range(10, 0, -1)           # 10,9,8,...,1 — negative step, counts down
range(0, 10, -1)             # empty! direction and step must agree, or you get nothing

range() doesn’t build a real list in memory — it’s a lazy sequence that produces numbers on demand. list(range(5)) forces it into an actual list if you need one.

4. while loop — runs as long as a condition stays True.

python
count = 0
while count < 5:
    print(count)
    count += 1          # MUST change something that affects the condition, or infinite loop

Use while when you don’t know in advance how many iterations you need (waiting for valid input, game loops, retry logic) — use for when you’re iterating over a known collection or a fixed range.

5. The infinite loop pattern — intentional, and a real tool

python
while True:
    command = input("> ")
    if command == "quit":
        break

This is correct and common — “loop forever, until something inside explicitly decides to stop.” You’ve already used this correctly in your inventory shell.

6. break — in full. Immediately exits the nearest enclosing loop, skipping any remaining code in that loop, including any else clause (point 11).

python
for n in range(100):
    if n == 5:
        break
    print(n)
# prints 0,1,2,3,4 then stops entirely

7. continue — in full. Skips the rest of the current iteration only, then resumes the loop at the next item/check. Doesn’t exit the loop.

python
for n in range(10):
    if n % 2 != 0:
        continue       # skip odd numbers, but keep looping
    print(n)
# prints 0,2,4,6,8

8. pass — in full. A no-op placeholder, needed wherever Python’s grammar requires some statement but you have nothing to put yet.

python
for item in items:
    if item.is_broken:
        pass             # TODO: handle this later — but code must still be syntactically valid
    else:
        process(item)

pass is also common in empty function/class bodies during early design, before you’ve filled them in.

9. break/continue/pass and nested loops. They only ever affect the innermost loop they’re textually inside:

python
for i in range(3):
    for j in range(3):
        if j == 1:
            break          # only breaks the INNER loop
        print(i, j)

To break out of multiple nested loops at once, Python has no built-in multi-level break. Common fixes:

python
# Option A: a flag
found = False
for i in range(3):
    for j in range(3):
        if some_condition:
            found = True
            break
    if found:
        break

# Option B (often cleaner): wrap in a function and `return`
def search():
    for i in range(3):
        for j in range(3):
            if some_condition:
                return i, j

10. enumerate() — index + value together. Replaces manually tracking a counter variable:

python
for i, word in enumerate(["a", "b", "c"]):
    print(i, word)
# 0 a / 1 b / 2 c

for i, word in enumerate(["a", "b", "c"], start=1):   # custom starting number
    print(i, word)
# 1 a / 2 b / 3 c

This directly replaces the clumsier for i in range(len(words)): word = words[i] pattern.

11. The for/while ... else clause — genuinely unique to Python. The else block runs only if the loop completed naturally, without hitting break:

python
for name in names:
    if name == target:
        print("Found!")
        break
else:
    print("Not found anywhere.")   # only runs if the loop never broke

Mental model: “else” here doesn’t mean “otherwise” like in if/else — it means “no-break.” This is the cleanest built-in way to express “search and report failure,” without a separate found = False flag variable.

12. zip() — looping over multiple sequences in lockstep

python
names = ["Asha", "Rohit", "Meera"]
scores = [82, 55, 91]

for name, score in zip(names, scores):
    print(name, score)

zip() stops at the shortest input — if the lists are different lengths, extra items in the longer one are silently dropped. zip(a, b, c) works with three or more sequences at once too. Wrap in list() to see it materialized: list(zip(names, scores)) gives [("Asha",82), ("Rohit",55), ("Meera",91)] — a list of tuples.

13. Looping over a dict — all three forms, with intent

python
for key in d:              # keys only (default)
for key in d.keys():        # same, more explicit/readable
for value in d.values():     # values only
for key, value in d.items():  # both — the one you'll use most

14. Modifying a collection while looping over it — the trap, formalized. Changing a list’s length while iterating it by position shifts every later index, silently skipping or repeating items. Changing a dict’s or set’s size during iteration raises RuntimeError outright. The fix is always the same: loop over a copy.

python
for x in my_list[:]:              # loop over a COPY (slice)
    if x < 0:
        my_list.remove(x)

for key in list(my_dict.keys()):    # loop over a COPY of the keys
    if my_dict[key] == 0:
        del my_dict[key]

15. Iterators vs iterables — the mechanism underneath every loop (preview of generators, coming later). An iterable is anything with an __iter__ method (lists, strings, dicts...). Calling iter() on it produces an iterator — an object with a __next__ method that hands out one value at a time and raises StopIteration when exhausted. A for loop is really just syntactic sugar for:

python
it = iter(my_list)
while True:
    try:
        item = next(it)
    except StopIteration:
        break
    print(item)

You don’t need try/except yet to use for loops — Python handles this translation invisibly — but knowing it exists demystifies what a for loop actually is under the hood, and sets up generators later.

16. Performance notes. for loops over a known collection are generally preferred over while with a manual counter — fewer places to introduce an off-by-one or infinite-loop bug. List comprehensions (which you’ve learned) are often faster than an equivalent for + .append() loop, for the same reason mentioned before: Python optimizes that specific pattern internally.

17. Common bugs, as a checklist (several of which you’ve already hit and fixed):

Off-by-one: range(n) vs range(n+1) — your 001_for_loop_01 bug.
Infinite while: forgetting to update the condition variable — your 003_for_and_while_loop_03 bug.
Modifying a list/dict while looping over it by position or key.
Confusing break (stop entirely) with continue (skip this one).
Shared mutable default in a loop-building function — the board=[] trap, relevant whenever a loop builds up a mutable object across calls.

# Day 1 (Full): Basics & Syntax

## Theory

**1. How Python actually executes a file.** Python is an **interpreted** language — it reads your file top to bottom and executes each line as it goes, rather than compiling the whole program first like C or Java. (Technically it compiles to an intermediate **bytecode** first, invisibly, then the Python Virtual Machine runs that — but from your perspective as a programmer, it behaves line-by-line.) This explains a very specific and useful fact: if there's a `NameError` on line 50, everything *before* line 50 still runs successfully first, in order.

**2. Indentation is syntax, not style.** This is the single biggest structural difference from most other languages. Python uses indentation (whitespace) to define code blocks — there are no `{ }` braces, no `begin`/`end` keywords.
```python
if True:
    print("inside the if")   # indented = inside the block
    print("also inside")
print("outside the if")        # not indented = outside the block
```
Mixing tabs and spaces, or inconsistent indentation levels, raises `IndentationError`. The convention (PEP 8, Python's official style guide) is **4 spaces** per level — virtually every editor, including VS Code, defaults to this.

**3. Statements end at the newline, not a semicolon.** No `;` is needed at the end of a line (you removed these from your own code earlier). A semicolon *can* be used to put multiple statements on one physical line, but it's considered poor style and almost never used in real Python:
```python
print("a"); print("b")      # legal, but avoid this
```
A single statement can be deliberately continued across multiple lines using a backslash `\`, or — more commonly and more cleanly — by wrapping in parentheses, brackets, or braces, which let Python know the statement isn't finished yet:
```python
total = (1 + 2 +
         3 + 4)              # parentheses make the line-break safe, no backslash needed
```

**4. The colon `:` — what it actually means.** Every block-starting line (`if`, `for`, `while`, `def`, `class`, `match`) ends in a colon. The colon is what tells Python "an indented block follows." Forgetting it is a `SyntaxError`, not a logic bug — Python catches it before your code even runs.

**5. Comments**
```python
# this is a comment — ignored entirely by Python
x = 5  # can also follow code on the same line
```
Triple-quoted strings (`"""..."""`) are **not** true comments — they're real string objects. If not assigned to a variable or used as a docstring, Python evaluates them and immediately discards the result, which works but isn't technically "a comment" in the same sense `#` is.

**6. Variable naming — the complete rule set**
- Must start with a letter (a-z, A-Z) or underscore `_` — never a digit.
- After the first character: letters, digits, underscores, in any combination.
- Case-sensitive: `score`, `Score`, and `SCORE` are three entirely different variables.
- Cannot be a reserved keyword (`if`, `for`, `class`, `return`, `None`, `True`, `False`, `and`, `or`, `not`, `is`, `in`, `lambda`, `def`, `pass`, `break`, `continue`, etc. — Python has about 35 of these, reserved and unusable as names).
- No spaces, no hyphens (`my-var` is invalid — Python reads `-` as subtraction).

**7. Naming conventions (not enforced by Python, but expected everywhere in real code):**
```python
snake_case          # variables and functions: total_score, calculate_average
PascalCase              # class names (coming in OOP): Student, InventoryItem
UPPER_CASE                 # constants — values that shouldn't change: MAX_ATTEMPTS = 5
_leading_underscore            # convention for "internal use" — a soft signal, not enforced
```

**8. Multiple assignment — every form**
```python
a, b, c = 1, 2, 3          # unpack three values at once, positions must match in count
x = y = z = 0                 # all three names point to the SAME value (chained assignment)
a, b = b, a                      # swap — Python builds an invisible tuple (b, a) first, then unpacks it
first, *rest = [1, 2, 3, 4]        # "starred" unpacking — first=1, rest=[2,3,4] (you met this with tuples)
```

**9. Everything in Python is an object — even the "simple" stuff.** `5`, `"hi"`, `True`, and even functions and classes themselves are all objects, each with a type and a unique identity in memory (`id(x)`). This single design choice is *why* functions can be stored in variables and passed around (Day's functions topic), why `bool` can be a subtype of `int`, and why `is` checks object identity rather than value.
```python
x = 5
type(x)        # <class 'int'>
id(x)            # some memory address, as a number
```

**10. Dynamic typing — what it means precisely.** A variable isn't *declared* with a fixed type the way it is in Java or C (no `int x = 5`). A name is just a **label** pointing at whatever object you last assigned to it, and that label can be reassigned to point at a completely different type at any time:
```python
x = 5          # x labels an int
x = "hello"       # now x labels a str — completely legal, no error
x = [1, 2, 3]       # now a list
```
This is powerful but also exactly why careless reuse of a variable name for different purposes mid-program can cause confusing bugs — Python won't stop you, so discipline is on you.

**11. Keywords you can't use as names — the complete list, for reference:**
```
False  None   True   and    as     assert  async  await
break  class  continue  def  del   elif    else   except
finally  for  from  global  if  import  in  is
lambda  nonlocal  not  or  pass  raise  return  try
while  with  yield
```
You've already met most of these in practice; several (`async`, `await`, `yield`, `nonlocal`, `global`, `lambda`, `raise`, `try`/`except`/`finally`, `with`, `assert`, `del`, `import`) are upcoming or recently-touched topics.

**12. Blank lines and whitespace.** Python ignores blank lines entirely — they're purely for human readability, used by convention to visually separate logical sections (e.g., two blank lines between top-level function/class definitions, per PEP 8). Extra spaces around operators (`x = 5` vs `x=5`) are also stylistic, not functional — Python doesn't care, but consistent spacing is expected in professional code.

**13. The `.py` file itself — the module concept, previewed.** Every `.py` file is automatically a complete, self-contained unit Python can either run directly or `import` elsewhere (fully covered in your modules topic). There's no special "project file" or "main file" requirement at the language level — any `.py` file can be the entry point.

**14. Running a Python file, and what happens on error.** Running `python filename.py` executes top to bottom. If an error occurs partway through, everything *already executed* has already had its effects (prints already happened, files already written) — Python doesn't roll anything back. This is worth knowing precisely because it explains why, in your own early code, a crash midway through a program still left partial `print()` output on screen before the traceback appeared.

**15. The `#!/usr/bin/env python3` shebang line — a brief, honest mention.** On Mac/Linux, a file can start with this special comment-like line to make it directly executable as a script from the terminal without typing `python` first. Irrelevant on Windows (your environment), but worth recognizing if you ever see it at the top of someone else's `.py` file.

**16. PEP 8 — Python's official style guide, briefly.** Not enforced by the language itself (your code runs fine either way), but it's the de facto standard every professional codebase expects: 4-space indents, `snake_case` names, blank lines between functions, max line length around 79-99 characters, spaces around operators. Tools like `black` or `flake8` can auto-check or auto-format code against it — worth knowing this exists, even before you use it.

Theory

2. Checking a type

python
type(5)              # <class 'int'>
type(5.0)              # <class 'float'>
type("5")                # <class 'str'>
type(True)                 # <class 'bool'>
type(None)                   # <class 'NoneType'>

3. int — unlimited precision, a genuine Python feature. Unlike many languages where integers overflow past a fixed size, Python int grows as large as memory allows:

python

4. int literals — different bases

python
0b1010       # binary — 10
0o12           # octal — 10
0xA              # hex — 10
1_000_000          # underscores allowed as readability separators — still just 1000000

5. Division — the two operators, and why they’re separate on purpose

python
10 / 3      # 3.333... — TRUE division, ALWAYS returns float, even 10 / 2 = 5.0
10 // 3      # 3 — FLOOR division, returns int if both inputs are int, float if either is float
10.0 // 3       # 3.0 — still floor division, but result type matches input type

Python deliberately split / into two operators (unlike languages where / behaves differently depending on operand types) specifically so division is always predictable regardless of input types.

6. Float imprecision — the real mechanism, not just “floats are weird.” Floats are stored in binary, and most decimal fractions (like 0.1) can’t be represented exactly in binary, the same way 1/3 can’t be written exactly in decimal.

python
0.1 + 0.2             # 0.30000000000000004, not 0.3
0.1 + 0.2 == 0.3         # False!
round(0.1 + 0.2, 2) == 0.3    # True — rounding masks the imprecision
abs((0.1 + 0.2) - 0.3) < 1e-9   # the "real" way to compare floats for near-equality

Rule to live by: never use == to compare floats directly. Either round both sides to a sensible precision first, or check that the difference is smaller than a tiny tolerance.

7. bool is literally a subtype of int — not just “acts like one.”

python

True == 1                      # True
False == 0                       # True
True + True                        # 2 — actual integer addition
True + 1                             # 2
[1, 2, 3][True]                        # 2 — True used as an index! Equivalent to [1,2,3][1]

This is a real, load-bearing language design choice — sum([True, True, False, True]) correctly gives 3, which is exactly how you’d count True values in a list of boolean results without writing a manual loop.

Day 6 (Full): Conditionals
Theory

1. The basic structure, formalized. if/elif/else evaluates conditions top to bottom and runs only the first block whose condition is True — every later elif/else is skipped, even if they’d also be True. This is the same “stop at first match” principle you’ve now seen in match/case too.

python
if condition1:
    ...
elif condition2:
    ...
elif condition3:
    ...
else:
    ...

elif and else are both optional. You can have a lone if, an if/else, or any number of elifs.

2. What counts as a condition. Any expression that evaluates to something truthy or falsy — not just bool values:

python
if my_list:          # True if non-empty
if name:                # True if non-empty string
if count:                # True if non-zero
if user_input.strip():     # common real pattern: True only if there's non-whitespace text

3. Nested conditionals — and why flattening usually wins. You already applied this fix to check_loan_eligibility. Nesting works, but each level of indentation adds mental load for whoever reads it:

python
# Nested — harder to scan
if age >= 18:
    if income >= 25000:
        if credit_score >= 700:
            print("Approved")
        else:
            print("Low credit")
    else:
        print("Low income")
else:
    print("Underage")

# Flattened with early returns — reads top to bottom, each line is one clear rule
def check(age, income, credit_score):
    if age < 18:
        return "Underage"
    if income < 25000:
        return "Low income"
    if credit_score < 700:
        return "Low credit"
    return "Approved"

Early returns only work cleanly inside a function — outside one, flattening usually means restructuring with elif chains instead, since there’s no return to exit early.

4. Ternary (conditional) expression — one-line if/else for picking a value. Same concept you met in comprehensions:

python
status = "pass" if score >= 50 else "fail"

This is an expression (produces a value to use), not a statement (a standalone action) — that distinction matters: you can put a ternary inside a function call, an f-string, a list, anywhere a value is expected. A full if/else block cannot be used that way.

5. Chained comparisons — a genuine Python-specific feature. Most languages require and:

python
if 0 <= age < 18:               # equivalent to: age >= 0 and age < 18
if 18 <= age <= 65:                # a clean range check

Chained comparisons can go further than two links: a < b < c < d checks all three relationships at once, short-circuiting if any link fails.

6. Combining conditions properly — and / or / not, not bitwise operators. This is the exact 013_challenge_05 bug, now formalized as a rule: &, |, ~ are bitwise operators (binary math), not logical ones. Always use and, or, not for conditions:

python
if age >= 18 and has_id and has_permission:      # correct
if age >= 18 & has_id & has_permission:            # WRONG — bitwise, different meaning entirely, may crash or silently misbehave

7. Short-circuit evaluation, applied to safety. and/or stop evaluating as soon as the result is certain — this isn’t just a performance detail, it’s a defensive coding tool:

python
if user is not None and user.is_active:
    # safe: if `user is None`, Python NEVER evaluates `user.is_active`,
    # so it can't crash trying to access .is_active on None

Order matters here — the safety check must come first in the and chain.

8. in and not in as conditions — membership checks, working on lists, strings, dicts (checks keys), sets, tuples:

python
if "the" in words:
if command not in ("quit", "exit", "q"):
if "@" in email:

9. Comparing different types. == between genuinely incompatible types (like 5 == "5") is always False — Python doesn’t raise an error, it just reports they’re not equal, which can silently hide bugs if you expected a type conversion to have already happened (your Q3-style traps, applied here).

10. is None vs == None. Always prefer is None / is not None for checking against None specifically:

python
if value is None:        # correct, idiomatic
if value == None:          # works, but non-idiomatic; `is` is preferred because None is a singleton

This connects to point 7 in Day 3 (operators) — identity checks are the intended use of is, and None checks are the main real-world case for it.

11. Guard clauses — conditionals as early exits, a pattern beyond just functions. Checking for bad/edge-case input first and exiting/skipping immediately, rather than wrapping the “main” logic in a big nested if:

python
def process(items):
    if not items:
        return "Nothing to process"

    # main logic, unindented, reads cleanly
    total = 0
    for item in items:
        total += item
    return total

12. Common conditional bugs, as a checklist:

&/| instead of and/or (bitwise vs logical) — your 013 bug.
== None instead of is None — works, but not idiomatic.
Comparing a converted vs unconverted type ("5" == 5 is always False).
Assuming elif chains “continue checking” after a match — they don’t; first match wins and the rest are skipped entirely.
Forgetting that bool("False") is True — any non-empty string is truthy, regardless of its text content (your own earlier discovery, directly relevant here since conditions are exactly where this bites).

3. Why from module import * is discouraged. It dumps every public name from that module directly into your file, with no prefix. If two modules both define process(), the second import silently overwrites the first, and you won’t know which one you’re actually calling. Always prefer explicit imports or the module.name form — it documents where something came from.

5. if __name__ == "__main__": — one of the most important patterns in Python. Every module has a hidden variable __name__. When a file is run directly, __name__ equals "__main__". When that same file is imported by another file, __name__ equals the module’s actual name instead.

python
# helpers.py
def greet(name):
    return f"Hello, {name}"

if __name__ == "__main__":
    print(greet("Test"))     # only runs when helpers.py is executed directly
    # does NOT run when another file does `import helpers`

This lets a file serve two purposes: a reusable module, and a standalone script with its own test/demo code, without the demo code firing every time someone just wants to import your functions.

### 5. List methods that change the original list

|---|---|

Examples:

Important difference:

```

### 8. References, aliasing and copying
This is one of the most important list concepts.
```

`is` checks whether objects are the same object.

### 9. Shallow copying and nested lists
A shallow copy copies only the outer list.

The inner lists are still shared.

### 10. The nested-list multiplication trap
Avoid this:
```
grid = [[0] * 3] * 3
```
All three rows refer to the same inner list.
```

print(grid)
```
Output:
```
[[7, 0, 0], [7, 0, 0], [7, 0, 0]]
```
Correct approach:
```
grid = []
for _ in range(3):
    grid.append([0] * 3)
```
Later, after learning comprehensions:
```
grid = [[0] * 3 for _ in range(3)]
```
Each iteration creates a fresh inner list.

### 12. Do not modify a list while looping over it

clean_items = []

### 15. Mutable default argument trap

## Topic: Tuples
## Theory
### 1. What is a tuple?
A tuple is an ordered, immutable sequence.
Once created, you cannot add, remove, or replace its elements.
```
point = (3, 4)
```
Lists are generally used for data that changes.
Tuples are generally used for fixed collections or records that should not change shape. Python’s documentation describes tuples as immutable sequences, often useful for heterogeneous records and values that can safely participate in sets or dictionary keys when their contents are hashable. [docs.python](https://docs.python.org/3/builtins/stdtypes.html)
***
### 2. Creating tuples
```
t = (1, 2, 3)
t = 1, 2, 3
```
Parentheses are optional when multiple values are separated by commas.
```
single = (5,)
```
The comma makes it a tuple.
```
not_a_tuple = (5)
```
This is only the integer `5` inside parentheses.
```
empty = ()
t = tuple([1, 2, 3])
t = tuple("abc")
```
Output:
```
('a', 'b', 'c')
```
The single-item tuple trap is one of the most common tuple mistakes:
> No comma means no tuple.
***
### 3. Indexing and slicing
Tuples support indexing and slicing exactly like lists.
```
t = (10, 20, 30, 40)
t[0]       # 10
t[-1]      # 40
t[1:3]     # (20, 30)
```
***
### 4. Immutability
```
t = (1, 2, 3)
t[0] = 99
```
Output:
```text
TypeError: 'tuple' object does not support item assignment
```
You cannot replace an item stored in a tuple.
***
### 5. Tuples can contain mutable objects
A tuple itself is immutable, but it can contain mutable objects such as lists.
```
t = ([1, 2], "fixed")
t[0].append(3)
print(t)
```
Output:
```
([1, 2, 3], "fixed")
```
This is allowed because the list object is mutated in place.
This is not allowed:
```
t[0] = [9, 9]
```
That tries to replace the item at position `0`, which would modify the tuple.
The tuple itself never changes shape, but mutable objects inside it can still change.
***
### 6. Tuple methods
Tuples have only two common methods because they are immutable.
```
t.count(value)
t.index(value)
```
```
t = (10, 20, 20, 30)
t.count(20)  # 2
t.index(30)  # 3
```
There is no:
```
t.append()
t.sort()
t.remove()
```
***
### 7. Packing and unpacking
Packing:
```
point = 3, 4
```
Unpacking:
```
x, y = point
```
Extended unpacking:
```
a, *middle, b = (1, 2, 3, 4, 5)
```
Results:
```
a       # 1
middle  # [2, 3, 4]
b       # 5
```
The starred target becomes a list.
Swapping variables:
```
x, y = y, x
```
Python creates values on the right side first, then unpacks them into the names on the left.
***
### 8. Why tuples exist
Tuples are useful for several important reasons.
- Returning multiple values from functions.
- Representing fixed-shape data such as coordinates and RGB colours.
- Using immutable values as dictionary keys or set members.
- Receiving data that should not be reordered or structurally modified.
- Understanding `zip()`, which produces tuples.
Example: multiple return values.
```
def divide(a, b):
    return a // b, a % b
quotient, remainder = divide(10, 3)
```
Example: coordinate as a dictionary key.
```
locations = {
    (0, 0): "Origin",
    (10, 20): "Point A"
}
```
A list cannot be used as a dictionary key because lists are mutable and unhashable. [docs.python](https://docs.python.org/3/tutorial/datastructures.html)
***
### 9. Hashability
A tuple is hashable only if every item inside it is hashable.
```
hash((1, 2, 3))
```
This works.
```
hash((1, [2, 3]))
```
This fails because a list is unhashable.
```text
TypeError
```
Examples:
```
(1, 2, 3)       # Hashable
("A", True, 5)  # Hashable
(1, [2, 3])     # Not hashable
```
***
### 10. Tuple comparisons
Tuples compare lexicographically, element by element.
```
(1, 2) < (1, 3)
```
Output:
```
True
```
Python compares:
```text
1 with 1
2 with 3
```
Since `2 < 3`, the full comparison is `True`.

## Docstrings
### 1. What is a docstring?
A docstring is a string literal placed as the first statement inside a module, function, class, or method.

def add(a, b):

print(add.__doc__)

Output:
```text
Return the sum of two numbers.
```
You can also inspect documentation using `help()`.
```
help(add)
```

### 2. Single-line docstrings

```
def square(number):

```
***
### 3. Multi-line docstrings
Use a multi-line docstring for more detailed explanations.
```
def calculate_total(price, quantity):
    """
    Return the total cost.
    Parameters:
        price: Price of one item.
        quantity: Number of items.
    """
    return price * quantity
```

## Recursion
### 1. What is recursion?
Recursion is the process of defining something in terms of itself.
A recursive function is a function that calls itself.
A physical-world example is two parallel mirrors facing each other. An object between them appears repeatedly in reflected images.
***
### 2. Recursive function
Python functions can call other functions.
A function can also call itself.
```
def function_name():
    function_name()
```
This is called recursion.
However, a recursive function must have a stopping condition. Without one, it continues until Python reaches its recursion limit and raises `RecursionError`.
***
### 3. Base case and recursive case
Every safe recursive function needs:
- A **base case**: the condition that stops recursion.
- A **recursive case**: the part where the function calls itself with a smaller or simpler problem.
Example: factorial.
```
def factorial(n):
    """Return the factorial of a non-negative integer."""
    if n == 0 or n == 1:
        return 1
    return n * factorial(n - 1)
```
```
print(factorial(5))
```
Output:
```text
120
```
Conceptually:
```text
factorial(5)
= 5 × factorial(4)
= 5 × 4 × factorial(3)
= 5 × 4 × 3 × factorial(2)
= 5 × 4 × 3 × 2 × factorial(1)
= 120
```
***
### 4. Safer factorial input
The simple factorial function should reject negative numbers.
```
def factorial(n):
    """Return n! for a non-negative integer."""
    if n < 0:
        raise ValueError("n must be non-negative")
    if n == 0 or n == 1:
        return 1
    return n * factorial(n - 1)
```
```
number = int(input("Enter a non-negative integer: "))
print(factorial(number))
print(factorial.__doc__)
```
For large values, recursion can hit Python’s recursion limit. Iterative solutions are often more practical for deeply repeated tasks.

## Sets
### 1. What is a set?
A set is an unordered collection of unique, hashable items.
```
info = {"Ajay", 19, False, 5.9, 19}
print(info)
```
A possible output is:
```
{False, 19, 5.9, 'Ajay'}
```
The displayed order is not something you should rely on.
Sets:
- Do not allow duplicate values.
- Do not support indexing.
- Are mutable containers.
- Require their elements to be hashable.
Important correction:
> A normal Python `set` is mutable. You can add and remove items after creating it.
What cannot be changed is an individual set element “in place” through indexing, because sets have no indexes. Set elements must also be hashable, so mutable types such as lists and dictionaries cannot be elements of a set. The official Python documentation treats dictionaries, lists, sets, and tuples as general-purpose built-in containers, while dictionaries and sets rely on hashable values for keys/elements. [docs.python](https://docs.python.org/3/tutorial/datastructures.html)
***
### 2. Creating sets
```
s = {1, 2, 3}
s = set([1, 2, 2, 3])
s = set("hello")
```
Possible outputs:
```
{1, 2, 3}
{'h', 'e', 'l', 'o'}
```
Create an empty set using:
```
empty = set()
```
Do not use this:
```
empty = {}
```
That creates an empty dictionary, not a set.
***
### 3. Sets require hashable items
This fails:
```
{[1, 2], 3}
```
Output:
```text
TypeError
```
This works:
```
{(1, 2), 3}
```
Lists are mutable and unhashable.
Tuples can be hashable if everything inside them is hashable.
***
### 4. Adding and removing items
```
s = {1, 2, 3}
s.add(4)
s.update([5, 6])
s.remove(4)
s.discard(4)
s.pop()
s.clear()
```
| Method | Meaning |
|---|---|
| `add(value)` | Add one item |
| `update(iterable)` | Add multiple items |
| `remove(value)` | Remove an item; raises `KeyError` if missing |
| `discard(value)` | Remove an item safely; no error if missing |
| `pop()` | Remove and return an arbitrary item |
| `clear()` | Remove all items |
`set.pop()` does not remove a predictable position because sets are unordered.
***
### 5. Set mathematics
Sets are especially useful for mathematical set operations.
```
a = {1, 2, 3}
b = {2, 3, 4}
```
| Operation | Code | Result |
|---|---|---|
| Union | `a | b` | `{1, 2, 3, 4}` |
| Intersection | `a & b` | `{2, 3}` |
| Difference | `a - b` | `{1}` |
| Symmetric difference | `a ^ b` | `{1, 4}` |
```
a | b
```
Everything in either set.
```
a & b
```
Only items present in both sets.
```
a - b
```
Items in `a` but not in `b`.
```
a ^ b
```
Items in exactly one of the sets.
Think of these operations using Venn diagrams.
***
### 6. Set comparisons
```
{1, 2} <= {1, 2, 3}
```
Output:
```
True
```
This asks whether the left set is a subset of the right set.
```
{1, 2, 3} >= {1, 2}
```
Output:
```
True
```
This asks whether the left set is a superset of the right set.
Readable method forms:
```
{1, 2}.issubset({1, 2, 3})
{1, 2, 3}.issuperset({1, 2})
{1, 2}.isdisjoint({3, 4})
```
`isdisjoint()` returns `True` when two sets have no common items.
***
### 7. Removing duplicates while preserving order
A set removes duplicates, but a set alone should not be used when output order matters.
Use a set for fast membership checking and a list for preserving order.
```
items = ["a", "b", "a", "c", "b"]
seen = set()
unique_in_order = []
for item in items:
    if item not in seen:
        seen.add(item)
        unique_in_order.append(item)
print(unique_in_order)
```
Output:
```
['a', 'b', 'c']
```
This pattern is common in real Python programs.

### 8. `frozenset`
`frozenset` is an immutable version of `set`.
```
frozen = frozenset({1, 2, 3})
```
You cannot add or remove items from a `frozenset`.
Because it is immutable and hashable when its contents are hashable, a `frozenset` can be used as a dictionary key or stored inside another set.

### 10. Why membership testing is fast in sets
When checking membership in a list:
```

```
Python may need to inspect items one by one.
With a set:
```

```
Python uses hashing, making membership checks typically much faster for large collections.
Use a set when:
- You need unique values.
- You frequently check membership.
- You need mathematical set operations.
- The order of items does not matter.

## Dictionaries
### 1. What is a dictionary?
A dictionary is a collection of key-value pairs.
```
student = {
    "name": "Alok",
    "age": 20
}
```
Instead of finding values by numeric position, dictionaries find values through meaningful keys.
A dictionary is often called a mapping or associative array. Dictionary keys must be unique and hashable. [docs.python](https://docs.python.org/3/tutorial/datastructures.html)
Modern Python dictionaries preserve insertion order as a language guarantee. However, dictionaries should still be chosen for key-based lookup rather than because you need list-like positional access.
***
### 2. Creating dictionaries
```
d = {}
d = {"name": "Alok", "age": 20}
d = dict(name="Alok", age=20)
d = dict([("a", 1), ("b", 2)])
```
***
### 3. Dictionary keys must be hashable
This works:
```
d = {(0, 0): "origin"}
```
This fails:
```
d = {[0, 0]: "origin"}
```
Output:
```text
TypeError
```
Lists cannot be dictionary keys because they are mutable and unhashable.
Dictionary values can be almost anything:
```
data = {
    "numbers": [1, 2, 3],
    "student": {"name": "Alok"},
    "function": print
}
```
***
### 4. Accessing values
```
d = {"name": "Alok", "age": 20}
d["name"]
d.get("name")
d.get("city", "N/A")
"name" in d
```
| Expression | Result |
|---|---|
| `d["name"]` | Returns the value; raises `KeyError` if missing |
| `d.get("name")` | Returns the value or `None` if missing |
| `d.get("city", "N/A")` | Returns `"N/A"` if missing |
| `"name" in d` | Checks keys only |
Use square brackets when a missing key means there is likely a bug.
```
student_id = d["student_id"]
```
Use `.get()` when missing data is normal.
```
city = d.get("city", "Unknown")
```
***
### 5. Adding and changing values
```
d = {"name": "Alok", "age": 20}
d["city"] = "Nagpur"
d["age"] = 21
```

Comprehensions
Theory
1. What a comprehension is. A compact way to build a list, dict, or set from a loop, in one line. It's not a new concept — it's the loops and conditions you already know, just rearranged. Every comprehension can be rewritten as a for loop, and when learning, it's worth doing that translation until it clicks.
2. List comprehensions — the base pattern
python
squares = [n * n for n in range(10)]
# is exactly equivalent to:
squares = []
for n in range(10):
    squares.append(n * n)
Read it left to right: "give me n * n, for each n in range(10)."
1. Adding a filter condition
python
evens = [n for n in range(20) if n % 2 == 0]
# equivalent to:
evens = []
for n in range(20):
    if n % 2 == 0:
        evens.append(n)
The if here filters — only items that pass get included.
1. Conditional expression INSIDE the comprehension (different from the filter above)
python
labels = ["even" if n % 2 == 0 else "odd" for n in range(5)]
# ['even', 'odd', 'even', 'odd', 'even']
This is a ternary expression (x if condition else y), deciding what value to put in, not whether to include it. Easy to confuse with #3 — the position of the if is the tell: if before for = ternary (value chooser); if after for = filter (gatekeeper).
1. Nested loops inside a comprehension
python
pairs = [(x, y) for x in range(3) for y in range(2)]
# equivalent to:
pairs = []
for x in range(3):
    for y in range(2):
        pairs.append((x, y))
Read left to right in the same order you'd nest the loops — the leftmost for is the outer loop.
1. Flattening a nested list — a genuinely common real task
python
matrix = [[1, 2], [3, 4], [5, 6]]

# [1, 2, 3, 4, 5, 6]

python

# {0:0, 1:1, 2:4, 3:9, 4:16}

python

1. There is no tuple comprehension. (n for n in range(5)) doesn't make a tuple — it makes a generator (a different, lazy tool, worth learning separately later). To get an actual tuple from a comprehension-like expression, wrap a list comprehension: tuple(n for n in range(5)).
2.  Nested comprehensions — a comprehension inside a comprehension, for genuinely 2D data:
python
grid = [[r * 3 + c for c in range(3)] for r in range(3)]
# [[0,1,2],[3,4,5],[6,7,8]]
This is also the correct fix for your earlier [[0]*3]*3 bug — each inner [0]*3 here is freshly built, not shared.
1.  When NOT to use a comprehension — this is the mastery-level judgment call. Comprehensions should read like a sentence. If you need multiple conditions, side effects (like printing), or more than one nested level that isn't genuinely 2D data, a comprehension becomes a worse read than a plain loop. Code that's "clever" but takes 30 seconds to parse is a bug waiting to happen for whoever reads it next — including future-you.
python
# Getting hard to read — borderline:
result = [x*2 for x in data if x > 0 if x % 2 == 0 if x < 100]
# Clearer as a loop:
result = []
for x in data:
    if x > 0 and x % 2 == 0 and x < 100:
        result.append(x * 2)
1.  Performance note. Comprehensions are usually slightly faster than the equivalent for + .append() loop, because Python optimizes the comprehension pattern internally. Worth knowing, but never worth sacrificing readability for a small speed gain.
2.  Walrus operator inside comprehensions (:=), for when you need to use a computed value twice without computing it twice:
python
results = [y for n in data if (y := n * 2) > 10]
# computes n*2 once, reuses it as both the filter check and the value

python

def increment():

A nested function "remembers" the variables from its enclosing function, even after that outer function has finished running. counter() above returns increment, and increment keeps its own private count alive — that's a closure. 15. Recursion — a function that calls itself, with a base case to stop:

python
def factorial(n):
    if n <= 1:          # base case — without this, infinite recursion

    return n * factorial(n - 1)

Opening a File

Before we can perform any operations on a file, we must first open it. Python
provides the open() function to open a file. It takes two arguments: the name of
the file and the mode in which the file should be opened. The mode can be 'r' for
reading, 'w' for writing, or 'a' for appending.

Here's an example of how to open a file for reading:

f = open('myfile.txt', 'r')

By default, the open() function returns a file object that can be used to read from
or write to the file, depending on the mode.

Modes in file

There are various modes in which we can open files.

1. read (r): This mode opens the file for reading only and gives an error if the file
does not exist. This is the default mode if no mode is passed as a parameter.
2. write (w): This mode opens the file for writing only and creates a new file if the
file does not exist.
3. append (a): This mode opens the file for appending only and creates a new file
if the file does not exist.
4. create (x): This mode creates a file and gives an error
if the file already exists.
5. text (t): Apart from these modes we also need to
specify how the file must be handled. t mode is used
to handle text files. t refers to the text mode. There is
no difference between r and rt or w and wt since text
mode is the default. The default mode is 'r' (open for
reading text, synonym
onym of 'rt' ).

6. binary (b): used to handle binary files (images, pdfs,
etc).

Reading from a File

Once we have a file object, we can use various
methods to read from the file.

The read( method reads the entire contents of the file
and returns it as a string.

f = open('myfile.txt', 'r')
contents = f.read()
print(contents)

Writing to a File

To write to a file, we first need to open it in write mode.

f = open('myfile.txt', 'w')

We can then use the write0 method to write to the file.

f = open('myfile.txt', 'w')

Keep in mind that writing to a file will overwrite its
contents. If you want to append to a file instead of
overwriting it, you can open it in append mode.

f = open('myfile.txt', 'a')
f.write( 'Hello, world!')

    pass                       # empty body — `pass` satisfies Python's syntax requirement

s1 = Student()                   # an INSTANCE — an actual object built from the blueprint
s2 = Student()
s1 is s2                            # False — two separate objects in memory, even though same class
type(s1)                               # <class '__main__.Student'>
isinstance(s1, Student)                   # True

3. __init__ — the constructor, precisely. Runs automatically the moment an instance is created, used to set up that object’s starting data. It’s a dunder method (double-underscore) — the first of many you’ll meet.

python
class Student:
    def __init__(self, name, age):
        self.name = name          # instance attribute — stored ON this specific object
        self.age = age

s1 = Student("Asha", 20)
s2 = Student("Rohit", 22)
print(s1.name, s2.name)              # Asha Rohit — fully independent storage

4. self — not a keyword, not magic, just a parameter. When you write s1.greet(), Python automatically rewrites this internally as Student.greet(s1) — self is simply how the method receives a reference to which object it’s operating on. The name self is pure convention (you could technically call it anything), but every Python developer alive expects it to be called self, and breaking that convention actively hurts readability for no benefit.

5. Instance methods — functions that live inside a class

python
class Student:
    def __init__(self, name, age):
        self.name = name
        self.age = age

    def greet(self):
        return f"Hi, I'm {self.name}"

    def have_birthday(self):
        self.age += 1                 # methods can read AND modify the object's own state

s1 = Student("Asha", 20)
print(s1.greet())                      # "Hi, I'm Asha"
s1.have_birthday()
print(s1.age)                            # 21

6. Instance attributes vs class attributes — the critical distinction.

python
class Student:
    school = "Delhi Public School"     # CLASS attribute — one copy, shared by every instance

    def __init__(self, name):
        self.name = name                 # INSTANCE attribute — separate copy per object

s1 = Student("Asha")
s2 = Student("Rohit")
print(s1.school, s2.school)                # same value — both read from the CLASS

Student.school = "New School"                # change it on the CLASS...
print(s1.school, s2.school)                     # ...and BOTH instances see the new value

s1.school = "Private Tutoring"                     # this creates an INSTANCE attribute on s1 ONLY,
print(s1.school, s2.school)                           # "shadowing" the class one — s2 is untouched

That last line is subtle and important: assigning s1.school = ... doesn’t change the shared class attribute — it creates a brand-new instance attribute on s1 specifically, which from then on hides the class attribute whenever you access it through s1.

7. The mutable class-attribute trap — your board=[] bug, reborn at the class level. This is a genuinely common real bug:

python
class ShoppingCart:
    items = []                 # DANGEROUS — one list, shared by EVERY instance

    def add(self, item):
        self.items.append(item)

cart1 = ShoppingCart()
cart2 = ShoppingCart()
cart1.add("Pen")
print(cart2.items)               # ['Pen'] — cart2 sees cart1's item! Same shared list.

The fix — always initialize mutable attributes inside __init__, not as class attributes:

python
class ShoppingCart:
    def __init__(self):
        self.items = []          # a FRESH list, created per instance, every time

cart1 = ShoppingCart()
cart2 = ShoppingCart()
cart1.add("Pen")                    # (assuming an add method)
print(cart2.items)                     # [] — correctly independent

Immutable class attributes (strings, numbers) are safe to share this way — it’s specifically mutable shared defaults (lists, dicts) that cause trouble, exactly the same root cause as the default-argument trap you already know.

8. Dynamic attributes — Python allows adding one outside __init__, though it’s usually a smell.

python
s1.favorite_color = "blue"      # legal — but s2 does NOT get this; only s1 has it now

In disciplined code, every attribute an object will ever have should be set in __init__, so anyone reading the class knows its full shape at a glance. Attributes appearing ad-hoc elsewhere in the code make objects harder to reason about.

9. Dynamic attribute access — functions for working with attributes by name (as text), not dot notation

python
hasattr(s1, "name")           # True — does this attribute exist?
getattr(s1, "name")             # "Asha" — same as s1.name, but the name can be a variable
getattr(s1, "nickname", "N/A")    # "N/A" — default value if the attribute doesn't exist, like dict.get()
setattr(s1, "age", 25)              # same as s1.age = 25
delattr(s1, "age")                     # same as del s1.age

These matter when the attribute name itself is only known at runtime — e.g., looping over a list of attribute names and checking/setting each one dynamically, something .dotname syntax alone can’t do.

10. __str__ and __repr__ — controlling how an object displays itself

python
class Student:
    def __init__(self, name):
        self.name = name

    def __str__(self):
        return f"Student: {self.name}"             # used by print(), str(), f-strings

    def __repr__(self):
        return f"Student(name={self.name!r})"         # used by the console/debugger, and as a fallback

s1 = Student("Asha")
print(s1)              # "Student: Asha" — uses __str__
f"{s1}"                   # also uses __str__
repr(s1)                     # "Student(name='Asha')" — uses __repr__
[s1, s1]                        # when printed, a LIST of objects uses __repr__ for each item, not __str__

The convention, worth internalizing precisely: __str__ should be readable, meant for end users. __repr__ should ideally be unambiguous enough that eval(repr(obj)) could rebuild an equal object — in practice this means showing the class name and exact field values, like the example above. If only __repr__ is defined and __str__ is missing, Python falls back to using __repr__ for print() too — so defining just __repr__ is a reasonable minimum when you don’t need two different views.

11. Methods that take extra arguments — identical rules to regular functions, self is simply always first

python
class Student:
    def __init__(self, name):
        self.name = name
        self.marks = []

    def add_mark(self, mark):
        self.marks.append(mark)

    def average(self):
        if not self.marks:            # guard clause — avoids ZeroDivisionError
            return 0
        return sum(self.marks) / len(self.marks)

    def add_marks(self, *marks):          # *args works exactly as in regular functions
        for mark in marks:
            self.marks.append(mark)

12. Checking equality between instances — the default behavior, and why it surprises people.

python
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

p1 = Point(1, 2)
p2 = Point(1, 2)
p1 == p2            # False! By default, == checks IDENTITY (same object), not matching field values

This feels wrong the first time you hit it — two objects with identical data aren’t considered “equal” unless you explicitly teach the class how to compare itself, via __eq__ (next OOP topic). Worth sitting with now so it isn’t a surprise later: without defining it yourself, == on your own objects behaves like is.

13. Why classes beat your parallel-list approach — concretely, using your own code. Your inventory shell tracked names and quantities as two separate lists, kept in sync purely by matching index position — correct, but fragile; any mismatch between the two lists’ lengths or ordering silently breaks everything.

python
class InventoryItem:
    def __init__(self, name, quantity):
        self.name = name
        self.quantity = quantity

    def __str__(self):
        return f"{self.name}: {self.quantity}"

items = [InventoryItem("Pen", 10), InventoryItem("Notebook", 4)]

for item in items:
    print(item)                     # uses __str__ automatically

Each item now carries its own name and quantity together, as one coherent thing — there’s no second list to keep synchronized, no index-matching to get subtly wrong. This is the real shift OOP brings: from managing parallel structures by hand to modeling things that naturally belong together.

14. A class is itself an object too — a brief, genuinely mind-bending but useful fact. type(Student) is <class 'type'> — classes are instances of a special class called type. You don’t need to act on this yet, but it’s why you can do things like Student.school = "New School" at all — the class itself is a live object you can inspect and modify, not just a static template.


Lambda Functions in Python

In Python, a lambda function is a small anonymous function without a
name. It is defined using the lambda keyword and has the following
syntax:

lambda arguments: expression

Lambda functions are often used in situations where a small function
is required for a short period of time. They are commonly used as
arguments to higher-order functions, such as map, filter, and reduce.

Here is an example of how to use a lambda function:

# Function to double the input
def double(x):
return x * 2

# Lambda function to double the input
lambda x: x * 2

The above lambda function has the same functionality as the double
function defined earlier. However, the lambda function is anonymous,
as it does not have a name.

Lambda functions can have multiple arguments, just like regular
functions. Here is an example of a lambda function with multiple
arguments:
Function to calculate the product of two numbers
def multiply(x, y):

# Lambda function to calculate the product of two numbers
lambda x, y: x * y

Lambda functions can also include multiple statements, but they are limited to a single
expression. For example:

# Lambda function to calculate the product of two numbers,
# with additional print statement
lambda x, y: print(f'{x} * {y}={x*y}')

In the above example, the lambda function includes a print statement, but it is still limited to a
single expression.

Lambda functions are often used in conjunction with higher-order functions, such as map, filter,
and reduce which we will look into later.

Map, Filter and Reduce

In Python, the map, filter, and reduce functions are built-in functions that allo
you to apply a function to a sequence of elements and return a new sequence
These functions are known as higher-order functions, as they take other
functions as arguments.

map

The map function applies a function to each element in a sequence and retur
a new sequence containing the transformed elements. The map function has
the following syntax:

map(function, iterable)

The function argument is a function that is applied to each element in the
iterable argument. The iterable argument can be a list, tuple, or any other
iterable object.

Here is an example of how to use the map function:

# List of numbers
numbers = [1, 2, 3, 4,5]

# Double each number using the map function
doubled = map(lambda x: x * 2, numbers)

# Print the doubled numbers
print(list(doubled))

In the above example, the lambda function lambda x: x * 2 is used to double
each element in the numbers list. The map function applies the lambda function
to each element in the list and returns a new list containing the doubled
numbers.

filter

The filter function filters a sequence of elements based on a given predicate (a
function that returns a boolean value) and returns a new sequence containing
only the elements that meet the predicate. The filter function has the following
syntax:

filter(predicate, iterable)

The predicate argument is a function that returns a boolean value and is applied
to each element in the iterable argument. The iterable argument can be a list,
tuple, or any other iterable object.


Here is an example of how to use the filter function:

# List of numbers
numbers = [1, 2, 3, 4,5]

# Get only the even numbers using the filter function
evens = filter(lambda x: x % 2 == 0, numbers)

# Print the even numbers
print(list(evens))

In the above example, the lambda function lambda x: x % 2 == 0 is used to filter
the numbers list and return only the even numbers. The filter function applies
the lambda function to each element in the list and returns a new list containing
only the even numbers.

reduce

The reduce function is a higher-order function that applies a function to a
sequence and returns a single value. It is a part of the functools module in
Python and has the following syntax:

reduce(function, iterable)

The function argument is a function that takes in two arguments and returns a
single value. The iterable argument is a sequence of elements, such as a list or
tuple.

The reduce function applies the function to the first two elements in the iterable
and then applies the function to the result and the next element, and so on. The
reduce function returns the final result.

Here is an example of how to use the reduce function:

from functools import reduce

# List of numbers
numbers = [1, 2, 3, 4, 5]

# Calculate the sum of the numbers using the reduce function
sum = reduce( lambda x, y: x + y, numbers)

# Print the sum
print(sum)

In the above example, the reduce function applies the lambda function lambda
x, y: x + y to the elements in the numbers list. The lambda function adds the two
arguments x and y and returns the result. The reduce function applies the
lambda function to the first two elements in the list (1 and 2), then applies the
function to the result (3) and the next element (3), and so on. The final result is
